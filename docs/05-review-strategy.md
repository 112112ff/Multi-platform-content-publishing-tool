# 评审策略与得分点

本文件用于把比赛评审规则转化为项目执行策略，确保开发和 Demo 都围绕得分点展开。

## 评审规则对照

### 作品完整度与创新性 40%

官方关注点：

- 产品设计合理性
- 功能完整度
- 交互流畅度
- 是否新颖有创意

本项目对应策略：

- 做完整链路：输入 -> 适配 -> 预览 -> 校验 -> 发布 -> 记录。
- 不只复制内容，而是生成不同平台风格版本。
- 增加平台适配理由，让用户知道为什么这样改。
- 增加发布健康分，让工具具备实用判断能力。
- 用一键示例内容保证演示顺畅。

验收标准：

- 四个平台生成结果明显不同。
- 至少一个平台能展示发布失败原因。
- 用户能编辑某个平台版本后再发布。
- 页面没有明显空壳区域。

### 开发过程与质量 40%

官方关注点：

- 架构清晰度与合理性
- 代码健壮度、逻辑、规范、可读性
- PR 数量与质量
- commit 分布合理性

本项目对应策略：

- 使用 `PlatformAdapter` 适配器架构。
- 每个平台逻辑独立，主流程只依赖统一接口。
- PR 拆小，每个 PR 只做一件事。
- PR 描述必须包含功能描述、实现思路、测试方式和分工说明。
- 两名成员都要有 commit 和 PR 参与。
- 每天持续提交，避免最后一天突击。

验收标准：

- README 能清楚说明如何新增平台。
- `main` 分支每次合并后可运行。
- PR 描述不为空，且与代码变更一致。
- commit 时间都在 2026-05-29 至 2026-05-31。

### 演示与表达 20%

官方关注点：

- Demo 视频清晰完整
- 是否清楚表达作品功能和效果

本项目对应策略：

- Demo 录制前准备固定示例内容。
- 视频中按用户路径讲，不按代码文件讲。
- 必须展示核心模块：Agent 输入、平台适配、健康分、真实投递、扩展架构。
- README 中放 Demo 视频链接，并确保外部可访问。

验收标准：

- Demo 视频 3 到 5 分钟。
- 有声音讲解。
- 覆盖主要功能和效果。
- 链接放在 README 中，且可播放。

## 为什么选择题目二

三个议题中，题目二最适合在 72 小时内做出完整 MVP：

- 真实用户问题明确，创作者多平台分发确实繁琐。
- 可以不接真实平台 API，但必须用 Webhook 真实投递完成可验证闭环。
- 平台差异和扩展架构都很适合 Demo 表达。
- 两人可自然拆分为“产品界面”和“适配器逻辑”。

题目三虽然技术感强，但需要处理 GitHub PR 获取、上下文理解、误报漏报控制和模型选择，72 小时内更容易做成不稳定半成品。

## 最小可获高分版本

必须做到：

- 内容输入完整。
- 一键载入示例内容。
- 四个平台差异化适配。
- 平台适配理由。
- 发布健康分和校验问题。
- Webhook 真实投递。
- 投递结果记录。
- README 中的架构设计和扩展平台说明。
- 合规的 PR 与 commit 过程。

## 额外加分方向

有余力时优先做：

- 平台策略面板。
- 导出 Markdown。
- 发布结果可复制。
- 页面截图放入 README。
- 简单的本地存储草稿。

不优先做：

- 真实平台 API 发布。
- 复杂登录系统。
- 复杂数据库。
- 依赖外部大模型完成核心 Demo。
