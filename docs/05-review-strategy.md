# 评审策略与得分点

本文件用于把比赛评审规则转化为项目执行策略，确保开发和 Demo 都围绕得分点展开。

## 评审规则对照

### 作品完整度与创新性 40%

官方关注点：

- 产品设计合理性
- 功能完整度
- 交互流畅度
- 是否新颖有创意

本项目对应策略：

- 做完整链路：输入 -> 适配 -> 预览 -> 校验 -> 发布 -> 记录。
- 不只复制内容，而是生成不同平台风格版本。
- 增加平台适配理由，让用户知道为什么这样改。
- 增加发布健康分，让工具具备实用判断能力。
- 用一键示例内容保证演示顺畅。

验收标准：

- 六个平台生成结果明显不同，覆盖公众号、知乎、B站、小红书、微博、抖音。
- 至少一个平台能展示发布失败原因。
- 用户能编辑某个平台版本后再发布。
- 页面没有明显空壳区域。
- 线上 Demo 可以直接打开，并能通过“填入演示原文”快速跑通完整链路。

### 开发过程与质量 40%

官方关注点：

- 架构清晰度与合理性
- 代码健壮度、逻辑、规范、可读性
- PR 数量与质量
- commit 分布合理性

本项目对应策略：

- 使用 `PlatformAdapter` 适配器架构。
- 每个平台逻辑独立，主流程只依赖统一接口。
- PR 拆小，每个 PR 只做一件事。
- PR 标题必须用一句话说明新增或修改内容。
- PR 描述必须包含功能描述、实现思路和测试方式。
- 组队时在 PR 备注中补充具体分工。
- 两名成员都要有 commit 和 PR 参与。
- 每天持续提交，避免最后一天突击。

验收标准：

- README 能清楚说明如何新增平台。
- `docs/12-online-agent-proxy.md` 能解释线上 AI 代理部署方式和密钥边界。
- `main` 分支每次合并后可运行。
- PR 描述不为空，且与代码变更一致。
- 每个 PR 合并后都能复现演示效果。
- commit 时间都在 2026-05-29 至 2026-05-31。
- `npm run build`、`npm run test:run`、`npm run agent:check` 至少在最终提交前执行并记录。

### 演示与表达 20%

官方关注点：

- Demo 视频清晰完整
- 是否清楚表达作品功能和效果

本项目对应策略：

- Demo 录制前准备固定示例内容。
- Demo 先展示线上地址，再展示本地运行方式，降低用户复现成本。
- 视频中按用户路径讲，不按代码文件讲。
- 必须展示核心模块：Agent 输入、平台适配、健康分、真实投递、扩展架构。
- README 中放 Demo 视频链接，并确保外部可访问。

验收标准：

- Demo 视频 3 到 5 分钟。
- 有声音讲解。
- 覆盖主要功能和效果。
- 展示“填入演示原文 -> 生成六平台发布包 -> 编辑一个平台 -> 生成发布队列 -> 打开官方创作页 / Webhook 验证”。
- 链接放在 README 中，且可播放。

## 为什么项目聚焦题目二

本项目明确选择题目二“多平台内容发布工具”，所有功能都围绕创作者多平台分发问题展开：

- 真实用户问题明确，创作者多平台分发确实繁琐。
- 可以不接真实平台 API，但必须用 Webhook 真实投递或浏览器扩展 Bridge 完成可验证闭环。
- 平台差异和扩展架构都很适合 Demo 表达。
- 两人可自然拆分为“产品界面”和“适配器逻辑”。

## 最小可获高分版本

必须做到：

- 内容输入完整。
- 一键载入示例内容。
- 六个平台差异化适配。
- 平台适配理由。
- 发布健康分和校验问题。
- Webhook 真实投递。
- 浏览器扩展 Publisher Bridge。
- 投递结果记录。
- README 中的架构设计和扩展平台说明。
- 合规的 PR 与 commit 过程。

## 额外加分方向

有余力时优先做：

- 平台策略面板。
- 导出 Markdown。
- 发布结果可复制。
- 页面截图放入 README。
- 简单的本地存储草稿。
- 浏览器扩展填充更多平台字段，例如封面、合集、分区。

不优先做：

- 真实平台 API 发布。
- 复杂登录系统。
- 复杂数据库。
- 依赖外部大模型完成核心 Demo。
