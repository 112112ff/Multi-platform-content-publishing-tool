# 项目总览

## 项目名称

ContentBridge 内容桥

## 参赛议题

题目二：多平台内容发布工具

## 一句话介绍

ContentBridge 是一个面向创作者的多平台内容发布助手。用户可以粘贴已有原文，也可以输入一句自然语言需求；系统会识别标题、正文和标签，生成多个平台的可发布版本，并引导用户完成账号确认、发布体检、一键发送到平台草稿或测试接收端。

## 用户问题

很多创作者需要把同一份内容发布到公众号、知乎、B站、小红书、微博、抖音等平台，但不同平台的内容形态差异很大：

- 公众号更适合结构清晰、表达完整的长文。
- 知乎更看重观点、论证和问答语境。
- B站需要视频简介、分章、标签和互动引导。
- 小红书偏短句、生活化表达、话题标签和种草语气。
- 微博适合短观点、热点话题和评论互动。
- 抖音需要前 3 秒钩子、口播脚本和镜头提示。

手动改写会消耗大量时间，直接复制粘贴又容易造成风格不适配、标题过长、素材缺失、标签不足等问题。

## 产品定位

ContentBridge 不是简单复制粘贴工具，而是一个“发布助理”：

1. 识别用户粘贴的已有原文，提取标题、正文和标签。
2. 根据用户自然语言需求补全发布 Brief 和目标平台。
3. 使用 MiniMax Agent 生成平台化草稿，未配置 key 时降级到本地规则。
4. 在发布前做健康检查，减少发布失败和效果不佳的风险。
5. 只弹出当前目标平台账号确认，避免普通用户被复杂配置打断。
6. 在官方 API 难以接入的平台上，用浏览器扩展复用用户登录态，打开创作页并辅助填充草稿。
7. 用统一的适配器和发布桥架构支持后续扩展更多平台。

## MVP 范围

本期 72 小时内重点完成以下闭环：

```txt
用户粘贴原文或一句话输入
  -> 识别原文标题、正文、标签
  -> MiniMax Agent / 本地规则生成多平台草稿
  -> 用户确认目标平台账号
  -> 发布体检
  -> 浏览器扩展填充草稿 / 测试接收端真实 POST
  -> 展示结果和失败原因
```

## 明确不做

为了确保 72 小时内完成可演示 MVP，本期暂不做以下能力：

- 不直接保存用户平台账号、密码、Cookie 或 token。
- 不伪造已经发布到官方平台的成功结果。
- 不绕过任何平台审核或风控。
- 不做复杂多人在线协同编辑。
- 不承诺所有平台 DOM 自动填充 100% 成功，失败时提供草稿面板和复制兜底。

## 真实发布边界

当前真实可运行链路包括：

- MiniMax Agent：真实调用本地代理生成内容计划，代理未配置时自动降级。
- 测试接收端：真实 HTTP POST 到用户填写的接收 URL。
- 浏览器扩展 Publisher Bridge：打开平台创作页并尝试填充草稿，最终由用户人工确认发布。

## 作品亮点

- Agent 主流程更像普通用户能用的发布助手。
- 单平台确认降低理解成本，避免一上来展示六个平台配置。
- MiniMax 接入提升生成质量，同时保留稳定降级。
- 发布体检让工具不只是生成内容，还能提示发布风险。
- 浏览器扩展路线比“假装接官方 API”更适合国内内容平台。
- `PlatformAdapter`、Agent 平台目录和 Publisher Bridge 都能支撑更多平台扩展。

## 成功标准

作品完成后，应能在 Demo 中清晰展示：

- 用户输入一句内容需求。
- Agent 判断目标平台并生成草稿。
- 用户确认该平台账号。
- 系统展示发布体检和风险提示。
- 用户点击一键发布到平台草稿或测试接收端。
- 系统展示真实反馈，不伪造成功。
- README 和文档说明如何新增平台、如何配置 MiniMax、如何安装扩展。
