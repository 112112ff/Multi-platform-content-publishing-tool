# 开发协作与 PR 规范

## 目的

这份文档面向评审和协作者，说明 ContentBridge 的开发过程如何满足比赛对持续提交、PR 粒度和组队协作的要求。它只保留公开仓库需要展示的信息，不包含内部提示词或临时沟通内容。

## 协作原则

- 每个 PR 只做一件事。
- PR 标题用一句话说明新增或修改内容。
- PR 描述必须包含功能描述、实现思路、测试方式。
- 如果是组队提交，PR 备注中需要写清楚本 PR 的具体分工。
- 每个 PR 合并后，`main` 分支必须保持可运行。
- 不提交 `.env`、账号密码、Cookie、token 或任何私有密钥。

## 分工口径

最终分工以 GitHub 的 PR 作者、commit 作者和 PR 备注为准。README 和本文件只说明模块责任边界：

| 模块 | 主要内容 |
| --- | --- |
| 产品与前端体验 | 首页输入、发布 Brief、平台预览、发布队列、账号确认、结果反馈、Demo 路径 |
| 内容适配与平台规则 | `PlatformAdapter`、六平台标题/正文/标签生成、平台校验、发布体检 |
| 发布链路 | 官方创作页打开、浏览器扩展 Bridge、Webhook/测试接收端真实投递 |
| AI 与降级 | MiniMax 代理接入、线上健康检查、本地离线规则兜底 |
| 文档与提交 | README、架构设计、评委运行说明、Demo 脚本、依赖与原创功能说明 |

## PR 描述模板

仓库已提供 `.github/pull_request_template.md`。每个 PR 必须按以下结构填写：

```md
## 功能描述
说明本 PR 新增或修改了什么，用户如何使用。

## 实现思路
说明关键技术选型、核心逻辑、文件结构或设计取舍。

## 测试方式
说明如何验证功能正常运行，列出实际执行的命令或手工验收步骤。

## 备注
如使用第三方依赖、复用历史代码、有未完成事项，或组队时需要说明具体分工，请在这里说明。
```

## 推荐 PR 拆分

为了避免“最后一天一次性导入代码”的无效风险，大功能应拆成多个小 PR：

1. 项目规划和比赛规则文档。
2. React + TypeScript + Vite 项目骨架。
3. 内容与平台核心类型。
4. 平台适配器注册机制。
5. 公众号、知乎、B站、小红书、微博、抖音适配器。
6. 发布助理输入流程。
7. 多平台预览和编辑。
8. 发布体检与队列。
9. Webhook 真实投递。
10. 浏览器扩展 Publisher Bridge。
11. MiniMax 代理和离线降级。
12. README、Demo 脚本和评委运行说明。

## 合并前检查

- `npm install` 可安装依赖。
- `npm run build` 通过。
- `npm run test:run` 通过。
- 普通 `npm run dev` 能启动前端。
- 线上代理可通过 `https://contentbridge.onrender.com/api/agent-health` 检查。
- README 已列明依赖、原创功能、运行方式和能力边界。
- PR 描述与实际代码变更一致。
- 没有提交敏感信息。
