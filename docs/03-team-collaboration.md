# 团队协作与分工

## 协作原则

本项目由两名成员协作完成。比赛要求两名队员都必须使用各自 GitHub 账号提交 commit，并在 PR 中清晰描述分工。

协作目标：

- 每个人都有明确负责模块。
- 每个 PR 只做一件事。
- 主分支始终保持可运行。
- 避免最后一天集中导入代码。
- PR 描述和 commit 分布能体现真实开发过程。

## 推荐分工

当前暂按角色分工记录。队友加入后，需要把真实 GitHub 用户名补到这里和后续 PR 描述中。

```txt

成员 B：待补充队友 GitHub 用户名
```

## 分支命名

推荐格式：

```txt
feature/short-feature-name
docs/short-doc-name
fix/short-bug-name
```

如果由 Codex 创建分支，也可以使用：

```txt
codex/init-app-shell
codex/platform-adapters
codex/publish-simulator
```

## PR 标题规范

标题用一句话说明本 PR 做了什么。

示例：

```txt
初始化 React 工作台项目骨架
新增内容输入表单和示例内容
实现平台适配器接口与注册机制
实现小红书内容适配和校验规则
```

## PR 描述模板

每个 PR 必须包含：

```md
## 功能描述
说明本 PR 新增或修改了什么，用户如何使用。

## 实现思路
说明关键技术选型、核心逻辑、文件结构或设计取舍。

## 测试方式
说明如何验证功能正常运行。

## 分工说明
说明本 PR 由谁完成，是否依赖其他队员模块。
```

仓库已经提供 `.github/pull_request_template.md`，开 PR 时直接按模板填写。

## Commit 建议

提交信息保持清晰，不要使用无意义信息。

推荐：

```txt
docs: add project planning docs
feat: add content editor
feat: implement platform adapter registry
fix: handle missing video url validation
style: polish workspace layout
```

避免：

```txt
update
test
fix bug
111
```

## 避免冲突的方式

- 不要两个人同时大量修改 `README.md`。
- 不要两个人同时重写 `src/App.tsx`。
- 大功能先拆目录和接口，再分别填实现。
- 每次开始开发前先拉最新 `main`。
- 每个 PR 合并后，另一个人及时同步。

- 把仓库从 Private 改为 Public，确认未登录状态也能访问。
