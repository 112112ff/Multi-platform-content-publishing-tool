# PR 描述：优化 Agent 引导发布主流程

## 标题

优化 Agent 引导发布流程，补齐账号确认、浏览器扩展和真实投递闭环

## 功能描述

本 PR 聚焦把 ContentBridge 从“能看的发布工作台”收敛成“普通创作者能顺着走完的发布助手”。

主要改动：

- 新增发布流程指示：说出需求 -> 生成版本 -> 确认登录 -> 发送草稿。
- 将“平台账号连接”调整为“发布账号确认”，避免用户误以为系统会保存账号密码。
- 发送到浏览器扩展前，必须先确认本次目标平台已在浏览器登录；未确认时会阻断并提示下一步。
- 账号确认弹窗把本次需要的平台排在前面，并加“本次需要”标记。
- 将界面里的部分技术词调整为 C 端更容易理解的表达，例如“测试接收地址”。
- 修复 Agent 提取主题时出现“学习方法 和”这类不自然标题的问题。
- 修复全平台内容生成后发布任务数量不完整的问题，确保显式选择的平台都会进入发布计划。
- 补充测试，覆盖“显式选择的平台必须保留在发布计划中”的行为。

## 实现思路

- 继续保留当前左侧 Agent、右侧预览/发布的主布局，不做大范围改版。
- 在 `App.tsx` 中增加流程状态计算，把内容生成、账号确认和投递反馈映射成清晰步骤。
- 将浏览器扩展发布改成账号确认门槛：未确认登录时不发送任务，也不伪造成功。
- 在矩阵运营引擎里合并“内容匹配账号”和“用户显式选择平台”，避免平台预览和发布任务数量不一致。
- 通过 `dedupeAccounts` 保证账号任务不重复。
- 用 CSS 增加轻量流程指示、账号状态提示和本次目标账号高亮。

## 测试方式

已执行：

```bash
npm run build
npm run test:run
```

测试结果：

- 构建通过。
- 4 个测试文件通过。
- 12 条测试通过。

浏览器验收：

- 从首页点击快捷指令生成小红书/知乎版本。
- 检查流程指示出现，账号确认步骤显示“还差 2 个平台确认登录”。
- 未确认登录时点击“先确认登录，再发送草稿”，系统阻断并打开账号确认弹窗，不伪造成功。
- 确认知乎和小红书登录后，按钮变为“发送到浏览器扩展”；未安装扩展时显示明确失败原因。
- 使用本地测试接收端跑全平台投递，收到 6 个真实 POST，平台分别为 zhihu、bilibili、xiaohongshu、douyin、wechat、weibo。
- UI 显示“真实投递完成：共 6 个任务”。

## 能力边界

本 PR 不伪造官方平台发布成功。当前真实链路包括：

- 测试接收端/自建服务真实 HTTP POST。
- 浏览器扩展打开平台创作页并尝试填充草稿。

最终在官方平台页面的发布动作仍需用户人工确认。
